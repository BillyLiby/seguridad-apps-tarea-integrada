# 3.3b Pruebas automatizadas (pytest, `tests/test_security.py`)
Datos semilla: nota 1 y 3 = alice, nota 2 = bob. Usuarios ficticios: alice, bob (user), admin (admin).

| Prueba | Caso exigido | Condiciones de entrada | Comportamiento esperado | Aserciones |
|---|---|---|---|---|
| t1 | Acceso legítimo a recurso propio | Token de alice; `GET /notes/1` | La API entrega la nota | `status == 200`; `title == "Plan de Alice"` |
| t2 | Denegación de recurso ajeno | Token de alice; `GET /notes/2` (de bob) | Acceso denegado sin filtrar contenido | `status == 403`; `"Bob" not in body` |
| t3 | Sin autenticación válida | Sin cabecera Authorization | Rechazo | `status == 401` |
| t3b | Token alterado / `alg=none` | JWT firmado con otra clave; JWT sin firma | Rechazo de ambos | `status == 401` (x2) |
| t4 | Entrada inesperada | Título de 101 caracteres; campo extra `owner` | Validación rechaza | `status == 422` (x2) |
| t5 | Restricción por rol | `GET /admin/users` con alice y con admin | Solo admin accede | alice `403`; admin `200` y usuarios `{alice,bob,admin}` |
| t6 | Inyección SQL (negativa) | alice busca `q = x' OR 1=1 --` | No se filtran datos ajenos | `"Secreto de Bob" not in body` |
| t6b | Búsqueda legítima (positiva) | alice busca `q = Plan` | Solo su nota 1 | `status == 200`; ids `== [1]` |
| t7 | Trazabilidad del flujo | alice pide nota 2 con trazas activas | Se registran entrada, autenticación, denegación y respuesta | Mensajes `[1]`, `[2]`, `[4] DENEGADA`, `[5] ... 403` presentes |
| t8 | Token expirado | JWT bien firmado con `exp` pasado | Rechazo | `status == 401` |

Ejecución: `pytest` (versión segura) y `$env:APP_TARGET="app_vulnerable"; pytest` (versión vulnerable: fallan t2, t6 y t7).
