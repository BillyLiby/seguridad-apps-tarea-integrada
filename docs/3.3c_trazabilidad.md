# 3.3c Recorrido interno de una solicitud (trazas locales)

**Naturaleza de la evidencia:** instrumentación local con el módulo `logging` (logger `trace`) en `app_segura/main.py`, capturada por la prueba `test_t7_request_flow_trace`. **No es IAST**: no hay agente instrumentando la ejecución ni análisis de flujo de datos; solo registros escritos a mano en puntos de control.

**Solicitud observada:** `GET /notes/2` con el token válido de `alice`. La nota 2 pertenece a `bob`.

## Versión segura (captura C3a)
```
[1] entrada HTTP GET /notes/2
[2] autenticacion OK usuario=alice rol=user
[4] autorizacion por objeto DENEGADA: nota=2 dueno=bob solicitante=alice
[5] respuesta GET /notes/2 -> 403
```

| Etapa | Punto del código (`app_segura/main.py`) | Qué ocurre |
|---|---|---|
| [1] | middleware `trace_requests` | Entra la solicitud HTTP; se registra método y ruta |
| [2] | dependencia `current_user` | Se valida el JWT (firma HS256, `exp`, `iss`) y se carga el usuario y su rol desde la base de datos |
| (3) | `require_admin` | No se invoca: esta ruta no es administrativa (solo aplica a `/admin/users`) |
| [4] | `get_note` | Se lee la nota y se compara `row["owner"]` (`bob`) con el solicitante (`alice`): no coinciden, se deniega |
| [5] | middleware `trace_requests` | Se devuelve 403 sin contenido de la nota |

## Versión vulnerable (captura C3b)
```
[1] entrada HTTP GET /notes/2
[2] autenticacion OK usuario=alice rol=user
[5] respuesta GET /notes/2 -> 200
```
La etapa [4] no existe: la solicitud pasa de la autenticación directamente a la respuesta con la nota de bob. La prueba `test_t7` falla en la aserción que busca `[4] autorizacion por objeto DENEGADA`. Esto muestra, desde el interior de la aplicación, la causa raíz del defecto 1 (BOLA/IDOR): se autentica al usuario pero no se autoriza el acceso al objeto.

## Observación
La capa de autenticación funciona igual en ambas versiones (`[2]`); la diferencia está solo en la verificación de propiedad del recurso.
