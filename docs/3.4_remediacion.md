# 3.4 Remediación y pruebas de regresión

Versión vulnerable (didáctica, aislada): `app_vulnerable/main.py`. Versión corregida: `app_segura/main.py`.
Diferencias de código: `reports/diff_vulnerable_vs_segura.patch`.

## Defecto 1: BOLA/IDOR en lectura de notas (autorización por objeto)
| Campo | Detalle |
|---|---|
| Recurso afectado | `GET /notes/{note_id}` |
| Categoría | CWE-639; OWASP API Security Top 10 2023, API1:2023 Broken Object Level Authorization; ASVS 5.0 8.2.2 |
| Condiciones de reproducción | Usuario autenticado `alice` (token válido) solicita la nota 2, que pertenece a `bob` |
| Respuesta observada (antes) | HTTP **200** con el contenido de la nota de bob. `pytest` en `app_vulnerable`: `test_t2` falla con `assert 200 == 403` |
| Causa raíz | El endpoint verifica que el token sea válido (autenticación) pero no compara el propietario de la nota con el usuario autenticado (autorización por objeto). La traza interna muestra `[2] autenticación OK` y salta directo a `[5] respuesta -> 200`, sin etapa `[4]` |
| Impacto | Cualquier usuario autenticado puede leer notas de otros recorriendo identificadores consecutivos. Pérdida de confidencialidad |
| Cambio aplicado | En `get_note`, tras recuperar la fila: si `row["owner"] != user["username"]` se registra la denegación y se responde **403**. (Ver diff) |
| Retest (después) | `test_t2` pasa: 403 y sin contenido de bob. Traza: `[4] autorización por objeto DENEGADA` y `[5] ... -> 403` |
| Prueba negativa | `test_t2_user_cannot_read_other_users_note` |
| Prueba positiva (uso legítimo preservado) | `test_t1_owner_reads_own_note`: alice sigue leyendo su nota 1 con 200 |

## Defecto 2: Inyección SQL en búsqueda
| Campo | Detalle |
|---|---|
| Recurso afectado | `GET /search?q=` |
| Categoría | CWE-89; OWASP Top 10, categoría Injection; ASVS 5.0 1.2.4 |
| Condiciones de reproducción | Usuario `alice` busca `q = x' OR 1=1 --` |
| Respuesta observada (antes) | HTTP 200 con **todas** las notas, incluida la de bob: `[{"id":1,"title":"Plan de Alice"},{"id":2,"title":"Secreto de Bob"},{"id":3,"title":"Lista de Alice"}]`. `test_t6` falla en `app_vulnerable` |
| Causa raíz | La consulta se arma con una f-string que concatena `q` (y el usuario) al SQL: el cliente puede cerrar la cadena y alterar la condición `WHERE` con `OR 1=1`, y el `--` comenta el resto |
| Impacto | Lectura de filas de otros usuarios saltando el filtro por propietario. Con otra carga útil, potencial acceso a otras tablas (p. ej. `users`) |
| Detección por herramienta | Semgrep, regla propia `lab-sqlite-dynamic-sql`: 1 hallazgo en `app_vulnerable/main.py`, línea 224; 0 hallazgos en `app_segura`. Confirmado con `test_t6` |
| Cambio aplicado | Consulta parametrizada: `WHERE owner = ? AND title LIKE ?` con valores como parámetros; además `q` limitado a 1–50 caracteres |
| Retest (después) | `test_t6` pasa: la carga útil se trata como texto literal y devuelve lista vacía; Semgrep sin hallazgos |
| Prueba negativa | `test_t6_sql_injection_does_not_leak_other_users_data` |
| Prueba positiva | `test_t6b_legitimate_search_still_works`: `q = Plan` devuelve solo la nota 1 de alice |

## Comparación reproducible antes/después
- Pruebas automatizadas: `$env:APP_TARGET="app_vulnerable"; pytest` (3 fallan: t2, t6, t7) frente a `pytest` en la versión segura (10 pasan).
- Sondeo manual contra ambas versiones: `python tools/probe_api.py http://127.0.0.1:8001` (vulnerable) y `python tools/probe_api.py http://127.0.0.1:8000` (segura).

## Límites de esta evidencia
Se corrigieron dos defectos de la aplicación. Las 24 vulnerabilidades de dependencias (PyJWT y starlette) se tratan aparte, con la actualización de versiones y su retest con `pip-audit` (ver 3.2 y 3.5). La limitación de intentos de login (T5 de la matriz) no se implementó y queda como riesgo residual.
